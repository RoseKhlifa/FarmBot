# 05 · 商用硬化设计（PC-* 卡总纲）

维护者的首要目标是**商用**（次选公益、再次开源），首选部署形态是 **Docker**。
本文件是所有 `PC-xx` 硬化卡的总纲：把一个「能跑的自动化工具」变成「能对外收费、可运维、可审计」的服务需要补的东西。

---

## 0. 必须先读：合规与法律风险（我无法替你消除）

我要如实说明，不粉饰：

- **本项目是第三方游戏自动化（外挂/脚本）**：它复刻官方客户端协议、加载官方反作弊 WASM、代替真人执行农场/好友操作。**这几乎必然违反目标游戏的用户协议（EULA）与《网络游戏管理》相关规定**，游戏厂商有权封号，并可能主张不正当竞争或侵权。
- **对它收费（商用）会显著放大法律敞口**：无偿自用与「规模化售卖外挂服务并牟利」在法律责任上不是一个量级。国内已有「提供游戏外挂经营牟利」被以**非法经营罪 / 提供侵入、非法控制计算机信息系统程序、工具罪**追责的判例。**公益/免费分发同样可能侵权，只是牟利情节更重。**
- **托管他人 QQ/微信登录凭据（`login_buffer`/openid）= 你成为账号数据的实际控制者**：一旦泄露或被盗用，你要承担数据安全与个人信息保护（PIPL）责任。
- 我给出的 PC-* 卡是**技术与运维层面的硬化**（多租户隔离、限流、审计、备份、可观测）。它们能让服务更专业、更抗滥用，但**不能使一项本身违规的经营变得合法**。

**建议（非法律意见，请咨询专业律师）**：
1. 商用前做一次正式法律评估，明确所在司法辖区对「游戏辅助工具收费」的定性。
2. 若继续，优先考虑**风险更低的形态**：开源自托管（用户自担风险、你不碰用户凭据、你不收费），或转向**有授权的游戏**/官方开放 API 的自动化。
3. 无论何种形态，落实下面的凭据加密、审计、数据最小化——这既是合规基线，也是对用户负责。

> 下述 PC-* 卡按「假设你已完成法律评估并决定推进」来写。是否落地由你决定。

## 2. 关键设计要点（各卡展开在 `cards/PC-*.md`）

### PC-01 速率限制
- 每 IP + 每 token 双维度令牌桶；登录/短信/领卡等敏感端点更严。用 `golang.org/x/time/rate` 或内存滑窗；多实例场景预留 Redis 后端接口（但默认单实例内存即可，符合单容器部署）。
- 命中返回 429 + `Retry-After`；豁免内部健康检查路径。

### PC-02 多租户、配额与凭据加密
- **租户模型**：在 `users`/`accounts` 之上增加 `plan`（套餐：账号数上限、并发挂机数、功能开关）与 `tenant_id`（若做经销商/团队）。中间件在账号启动/新增时校验配额，超限拒绝。
- **凭据静态加密**：`wechat_accounts.login_buffer`、`credentials`、`sessions` blob 用主密钥（env `FARM_MASTER_KEY`，AES-256-GCM）加密后入库；密钥不入库、不入日志。DB 泄露不等于凭据泄露。
- **数据最小化**：不需要的用户信息不存；头像等可再生数据可清理。

### PC-03 备份与导出
- `cmd/farmbot backup` 子命令：SQLite `VACUUM INTO` 生成一致性快照到 `<DataDir>/backups/farmbot-<ts>.db`（时间戳由外部传入，避免脚本内取时钟）。
- 定时备份由**外部 cron/compose sidecar** 触发（不在应用内起后台时钟，保持进程单一职责）；保留 N 份滚动。
- 导出：管理端可下载单账号数据（便于用户迁移，也是 PIPL 的可携权基线）。

### PC-04 指标与监控
- `/metrics`（Prometheus 文本格式，或轻量 JSON）：在线账号数、每账号操作计数、WS 连接数、登录成功/失败、TSDK 心跳失败数、HTTP 时延分位。
- 指标端点走独立鉴权或仅内网可达（不暴露给普通面板用户）。

### PC-05 操作审计
- `audit_log` 表：`actor_user, action, target_account, ip, ua, detail_json, ts`。中间件在**写类**管理操作后落审计（谁启停了谁的账号、改了谁的配置、发了多少卡密）。
- 审计只增不改；提供管理端查询与按时间导出。这是计费纠纷与滥用追责的证据链。

### PC-06 安全响应头
- 统一注入 `X-Content-Type-Options:nosniff`、`X-Frame-Options:DENY`、`Referrer-Policy`、`Content-Security-Policy`（对 SPA 收敛 script/连接源）、生产启用 `HSTS`。
- 保留现状对 `/login-assets` SVG 的 CSP sandbox 加固，统一到该中间件。

### PC-07 健康分级与灰度
- `/api/health`(存活，快) 与 `/api/ready`(就绪：DB 可连、迁移已到位、必要资源已加载) 分离；compose/K8s 探针分别指向。
- 优雅排空：收到 SIGTERM 先停止接新请求与新账号启动，等在途完成再退出（配合 P6-01 优雅退出）。

## 3. 商用形态下的部署基线（配合 P7 Docker 优先）

- **单容器**：一个镜像内含 Go 后端（已内嵌前端+WASM+yyb），对外单端口。无 sidecar 强依赖。
- **反向代理终止 TLS**：容器前置 Caddy/Nginx/云 LB 负责 HTTPS 与证书续期；应用只跑 HTTP，信任 `X-Forwarded-*`（在 Gin 设 trusted proxies）。
- **密钥经 env/secret 注入**：`FARM_MASTER_KEY`（凭据加密）、`ADMIN_PASSWORD` 等经 compose secrets 或部署平台密钥管理注入，不写入镜像、不进 git。
- **数据卷**：`data/`（含 `farmbot.db` + `backups/`）挂命名卷；备份卷可单独挂到宿主便于外部拉取。
- **资源与并发**：按套餐规划单容器可承载的并发挂机账号数（每账号 = 1 WS + 1 wazero 实例，内存是主要约束），压测后写入运维文档；超出用多容器 + 账号分片（预留 PC-02 的 `tenant_id`/分片键）。

> 结论：商用的**技术**路线在本方案内是完备可交付的（Docker 单容器 + 硬化卡）。商用的**合规**前提不在技术范围内，务必先做 §0 的法律评估。
